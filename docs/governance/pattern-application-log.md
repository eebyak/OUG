> **Status:** *(to be set — see [Document Status](../index.md#document-status))* · **Version:** v3.0
> **What this document is.** A deliberate-choice audit, not a maturity scorecard. The [Design Signature](design-signature-founding.md) asks whether every one of 58 *principles* is honoured — principles are not optional. This document asks a different question: which of the 42 *patterns* from the [Design Pattern Register](design-pattern-register.md) were actually chosen as the structural response, where, and — just as importantly — where a principle was honoured by some other means entirely, without ever adopting the pattern built for it. That is not a gap. A principle can be satisfied by a single governance decision that never becomes a reusable pattern, the same way a well-written function doesn't need a design pattern wrapped around it to be correct.
> **Organising scheme.** Patterns are sorted here by the three-tier taxonomy borrowed deliberately from software architecture: **Architectural** (shapes the whole institution's structure), **Structural** (defines bounded roles, bodies, and composition), and **Dynamic** (governs flows — decisions, information, review cycles — over time). This is a different sort from the Design Pattern Register's thirteen thematic groups; the same 42 patterns, organised by a different question.

## IV. What This Detective Work Actually Found

**Patterns genuinely adopted and load-bearing in this session's own work**, not just pre-existing and referenced: DP-6 (Crossing Point — four separate instances), DP-20 and DP-21 (Governance Review Calendar and Permeability Architecture), DP-25 (Design-First Institution — practiced, not only documented), DP-32 (Embedded University — actively extended), DP-34 (Jurisdictional Map), DP-35 (Evaluated Term, closed directly in statute), DP-40 and DP-41 (Adaptive Cycle and Transformation Dashboard, now genuinely load-bearing inside a statute), and DP-1/DP-12 (Compliance Map, closed as the very last addition to this pass).

**Patterns deliberately left thin, and why that's a legitimate choice, not an oversight:** DP-4 (Need-Based Allocation) and several curriculum-domain patterns (DP-8, DP-9, DP-13, DP-17, DP-18) were not touched this session because this session's actual work was governance, federation, and Mission Hub architecture — not curriculum or finance. A pattern being thin here reflects where the session's attention actually went, not a judgment that the pattern doesn't matter. This is the "choose wisely" discipline you named: not every pattern needs equal investment in every pass.

**One finding that was open, and is now closed rather than merely flagged:** DP-35 (The Evaluated Term). Reading the pattern directly surfaced a real gap — no mid-term Rector review with named goals existed anywhere in this repository. Grundordnung § 4 Absatz 4 now closes it directly, including a self-referential safeguard against the review itself becoming a formality (see the entry above).

## V. Document Index — Which Patterns Each File Should Cite

The tables above are organised pattern-first: one row per pattern, naming where it lives. This index inverts that: one row per document, naming every pattern it implements. Several documents implement more than one — that's not duplication, it's a document doing several structural jobs at once, and each job deserves its own citation where the document actually does that work, not just a single blanket reference at the top.

**How to use this list:** for each document below, add a short note at the point in the text where the pattern is actually implemented — not just in the document's frontmatter — following the convention already used, by accident, in Mission Hub Permeability Architecture and the Programme Development Forum. A short parenthetical is enough: *"(implements DP-21, The Home That Challenges)"*.

## VI. How to Document Pattern Use, Going Forward

Three concrete practices, not just a principle:

**1. Cite the pattern by ID inside the document that implements it, at the point of implementation — not only in a separate register.** Several documents already do this by accident of good writing (Mission Hub Permeability Architecture's own name comes from DP-21; the Programme Development Forum uses "Decision Account" straight from DP-22) — but it happened because the language matched, not because anyone deliberately wrote "(implements DP-21)" into the text. Going forward, when a new governance mechanism is deliberately built as an instance of a named pattern, say so explicitly, in the document itself, the way the Register now does retrospectively. This is cheap, and it's the single highest-value habit — it means the correspondence doesn't have to be rediscovered by detective work again next time.

**2. Keep this Log itself as the standing index — updated, not rebuilt.** The Design Signature gets full editions because principles need re-scoring against evidence periodically. This Log should instead be edited incrementally: when a document is created or amended and it adopts, drops, or partially implements a pattern, this table's one row changes. It should almost never need a "Third Edition."

**3. Treat "Partial" and "Not adopted" as equally legitimate final states, not just waypoints toward "Adopted."** DP-7 (Designed Profile) not being built yet is an open task. DP-4 being thin because this session's work was elsewhere is not the same kind of gap — it's a scope boundary. Conflating the two in documentation produces false urgency around patterns nobody has actually decided to prioritize. Keeping the distinction explicit — as this document tries to, in Section IV — is itself part of documenting pattern use honestly.
